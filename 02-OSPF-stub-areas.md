# OSPF Stub Areas

**What is a stub area?**
A regular OSPF area contains all the LSAs that are generated by the routers in that area, and also the LSAs that are generated by the ABRs and ASBRs that are connected to that area.
Stub area types - A non-backbone area that limits route flooding and the size of the LSDB by not allowing certain types of LSAs to be advertised into the area. Depending om the type of stub area, they may block type 3 (inter-area) and type 5 (external) LSAs. Insted they rely on a default route, that is injected by the ABR, to reach destinations outside the local area.
Using stub areas can result in smaller routing tables, smaller LSDBs and less LSA flooding. 

There are four types of stub areas:
- **Stubby area - Standard stub area (Stub)**
    No Type 5 LSAs are allowed in the area, but Type 3 LSAs are still allowed. The ABR will inject a default route into the area as a Type 3 LSA.
    No ASBRs are allowed in the area. This leads to that we cant redistribute an external route from another area router into the stub area, since that would require a type 5 LSA to be generated.
- **Totally stubby area (TS)**
    No Type 3 and Type 5 LSAs are allowed in the area. The ABR will inject a default route into the area as a Type 3 LSA. The flip side of this is that it reduces the routing table even more and reduces the sizes and number of LSA exchanges, and thus making it more efficient.
    No ASBRs are allowed in the area. This leads to that we cant redistribute an external route from another area router into the stub area, since that would require a type 5 LSA to be generated.

- **Not-so-stubby area (NSSA)**
    Like an stubby area but ASBRs are allowed.
    No Type 5 LSAs are allowed in the area, but Type 3 LSAs are still allowed. The ABR will inject a default route into the area as a Type 3 LSA.
    ASBRs are allowed in the area, and they can generate Type 7 LSAs to advertise external routes within the NSSA. The ABR will then translate these Type 7 LSAs into Type 5 LSAs when advertising them to other areas.

    NSSA takes the advatage of a stub area, but also allows for some external routes to be advertised within the area, making it more flexible than a standard stub area.

- **Totally NSSA (NSSA-TS)**
    Like a totally stubby area but ASBRs are allowed.
    No Type 3 and Type 5 LSAs are allowed in the area. The ABR will inject a default route into the area as a Type 3 LSA.
    ASBRs are allowed in the area, and they can generate Type 7 LSAs to advertise external routes within the NSSA. The ABR will then translate these Type 7 LSAs into Type 5 LSAs when advertising them to other areas.


If the area contains a ABR that is configured as a stub, the following happens:
- The ABR will not advertise any Type 4 and Type 5 LSAs in this area
- Every internal router in the stubby area will ignore any received type 5 LSAs, they wont originate any type 5 LSAs.
- ABR will automatically inject a default route into the area as a type 3 LSA. 


**What are the usecases for stub areas?**
<br>
Its difficult to see the benefit of using stub areas in a small network, but in larger enterprise networks with many routers and routes, it can be very beneficial to use stub areas to reduce the size of the LSDBs and routing tables, and to reduce the amount of LSA flooding. At this scale, the benefits of using stub areas can be significant in terms of improving network performance and stability.

In a Larger enterprice network, with many branch offices, it can be beneficial to use stub areas for the branch offices, since they typically do not need to know about the entire topology of the network, but only how to reach the rest of the network. The branch office only need to know a way out to the rest of the network, and thus a default route is sufficient for them.
Depending on the requirements of the branch office, a standard stub area or a totally stubby area can be used. If the branch office needs to have some external routes advertised within the area, then a NSSA can be used instead. So mixing te different types of stub areas can be a good way to optimize the network design and performance, while still meeting the specific needs of each area.

**Virtual links**
<br>
All areas in an OSPF Autonomous system must be physically connected to the area 0, backbone area. In some cases a physical lik is not possible, then you can use a virtual link to connect two parts of a partitioned backbone trough a non-backbone area. Virual links are also known as transit area and must have full routing information, hence it cant be a stub area. 
`router ospf 1` followed by:
`area area-id virtual-link router-id`

Example of configuring Virtual links:
- a virtual link between two ABRs with router IDs
Router with router ID 1.1.1.1: `area 1 virtual-link 2.2.2.2` 
router with router ID 2.2.2.2: `area 1 virtual-link 1.1.1.1`
In this example, the virtual link is configured in area 1, which is a non-backbone area, and it connects the two ABRs with router IDs 1.1.1.1 and 2.2.2.2.
Router 2.2.2.2 is an ABR that is connected to both area 0 and area 1, and router 1.1.1.1 is an ABR that have a physical connection to other areas but not to area 0, and thus needs the virtual link to connect to the backbone area.

**Config a stub area**
Use the `area xx stub` command on every router in the area to define an area as a stub area. An exampel is to configure all routers in area 7: `area 7 stub`.

**Config a Totally Stub Area**
`area xx stub no-summary` will configure a Totally Stub area. An example is to configure all routers in area 8: `area 8 stub no-summary`

**Config a Not-So-Stubby Area**
`area xx nssa`


**Config a NSSA**
`area xx nssa no-summary`
